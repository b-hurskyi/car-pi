# Architecture

## Overview

The car computer consists of two primary software components:

```text
┌─────────────────────────────┐
│          Frontend           │
│                             │
│     React + TypeScript      │
│                             │
│    UI / visualization      │
└──────────────┬──────────────┘
               │
        WebSocket / HTTP
               │
┌──────────────▼──────────────┐
│           Backend           │
│                             │
│      Python + FastAPI       │
│                             │
│ telemetry / integrations    │
└──────────────┬──────────────┘
               │
        Telemetry Providers
               │
       ┌───────┼─────────┐
       │       │         │
      Mock   Replay     OBD-II
```

The Raspberry Pi will eventually run both the frontend and backend.

During development, both components can run locally on macOS.

## Frontend responsibility

The frontend is responsible for:

- presenting information to the driver
- rendering telemetry
- handling UI state
- sending user-level commands to the backend where appropriate

The frontend must not communicate directly with:

- serial devices
- OBD adapters
- CAN interfaces
- GPIO
- Linux-specific hardware APIs

It consumes application-level data from the backend.

## Backend responsibility

The backend provides the boundary between the UI and the operating system / hardware.

Responsibilities may eventually include:

- vehicle telemetry
- OBD-II
- GPS
- Bluetooth
- system metrics
- telemetry recording
- replay
- phone/device integrations

FastAPI is used as the application interface.

WebSocket should be used for continuously changing telemetry.

HTTP should be used where real-time streaming is unnecessary.

## Telemetry providers

Vehicle telemetry should not be coupled to a specific hardware implementation.

Conceptually:

```text
TelemetryProvider
        │
        ├── MockTelemetryProvider
        ├── ReplayTelemetryProvider
        └── ObdTelemetryProvider
```

Consumers should operate on normalized telemetry rather than provider-specific data.

For example, the UI should consume:

```json
{
  "speedKph": 72,
  "rpm": 2380
}
```

and should not care whether those values originated from:

- generated mock values
- a recorded trip
- an OBD-II adapter

## Development modes

### Mock mode

Used during early development.

No Raspberry Pi or vehicle is required.

Telemetry is generated by software.

### Replay mode

Planned for later development.

Recorded telemetry can be replayed at home, allowing UI and analytics development using realistic driving data without access to the vehicle.

### Vehicle mode

Uses actual vehicle telemetry sources such as OBD-II.

This mode should initially remain read-only.

## Communication

Initial real-time communication:

```text
Backend
   │
   │ WebSocket
   ▼
Frontend
```

An initial endpoint may eventually look similar to:

```text
/ws/telemetry
```

The exact API contract should be defined during implementation rather than treated as fixed by this document.

## Deployment direction

Development:

```text
MacBook
├── React frontend
└── Python backend
```

Target:

```text
Raspberry Pi
├── React frontend
└── Python backend
```

The architecture should avoid requiring Raspberry Pi hardware for normal feature development.

## Current milestone

The first implementation should contain only enough functionality to validate:

```text
MockTelemetryProvider
        ↓
telemetry application layer
        ↓
WebSocket
        ↓
React client
```

No persistence or real vehicle hardware is required for this milestone.

## Architectural constraints

Prefer:

- explicit component boundaries
- dependency inversion around hardware
- normalized application models
- replaceable data providers
- minimal runtime dependencies

Avoid:

- direct hardware access from UI
- giant service classes
- speculative abstractions
- infrastructure added before it is needed
- coupling domain/application logic to Raspberry Pi specific APIs
