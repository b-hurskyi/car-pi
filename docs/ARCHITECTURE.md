# Architecture

## Overview

The car computer consists of two primary software components:

```text
┌─────────────────────────────┐
│          Frontend           │
│                             │
│     React + TypeScript      │
│                             │
│    UI / visualization      │
└──────────────┬──────────────┘
               │
        WebSocket / HTTP
               │
┌──────────────▼──────────────┐
│           Backend           │
│                             │
│      Python + FastAPI       │
│                             │
│ telemetry / integrations    │
└──────────────┬──────────────┘
               │
        Telemetry Providers
               │
               │
              Mock
```

The Raspberry Pi will eventually run both the frontend and backend.

During development, both components can run locally on macOS.

## Frontend responsibility

The frontend is responsible for:

- presenting information to the driver
- rendering telemetry
- handling UI state
- sending user-level commands to the backend where appropriate

The frontend must not communicate directly with:

- serial devices
- OBD adapters
- CAN interfaces
- GPIO
- Linux-specific hardware APIs

It consumes application-level data from the backend.

## Backend responsibility

The backend provides the boundary between the UI and the operating system / hardware.

Responsibilities may eventually include:

- vehicle telemetry
- OBD-II
- GPS
- Bluetooth
- system metrics
- telemetry recording
- replay
- phone/device integrations

FastAPI is used as the application interface.

WebSocket should be used for continuously changing telemetry.

HTTP should be used where real-time streaming is unnecessary.

## Telemetry providers

Vehicle telemetry should not be coupled to a specific hardware implementation.

The current provider boundary is:

```text
TelemetryProvider
        │
        └── MockTelemetryProvider
```

`TelemetryProvider` supplies normalized snapshots without exposing how values are
produced. `MockTelemetryProvider` is the only current implementation and generates
changing, coherent demo values for development without hardware. Replay and OBD-II
providers remain future possibilities rather than implemented components.

Consumers operate on this normalized telemetry contract:

```json
{
  "speedKph": 72,
  "rpm": 2380,
  "gear": "D",
  "ignition": true,
  "engineRunning": true
}
```

The UI does not care whether those values originated from generated mock values or
a future provider.

## Communication

The backend exposes normalized snapshots at:

```text
/ws/telemetry
```

The current end-to-end flow is:

```text
MockTelemetryProvider
        ↓
FastAPI WebSocket
        ↓
React telemetry client
        ↓
UI
```

The frontend connects to the same origin. During local development, Vite proxies
the WebSocket path to the backend; this keeps machine-specific addresses out of
application code and remains compatible with hosting both components together.

## Development modes

### Mock mode

Used during early development.

No Raspberry Pi or vehicle is required.

Telemetry is generated by software.

### Replay mode

Planned for later development.

Recorded telemetry can be replayed at home, allowing UI and analytics development using realistic driving data without access to the vehicle.

### Vehicle mode

Uses actual vehicle telemetry sources such as OBD-II.

This mode should initially remain read-only.

## Deployment direction

Development:

```text
MacBook
├── React frontend
└── Python backend
```

Production target:

```text
Raspberry Pi
├── Chromium
│       │
│       ▼
└── FastAPI / Uvicorn
    ├── /              built React frontend
    ├── /health        HTTP health endpoint
    └── /ws/telemetry  telemetry WebSocket
```

Vite produces the static frontend build, but it is not part of the production
runtime. FastAPI serves the build and application endpoints from one origin, so
the browser does not need a hard-coded device address or cross-origin setup.

The architecture should avoid requiring Raspberry Pi hardware for normal feature development.

## Current milestone

The current implementation validates:

```text
MockTelemetryProvider
        ↓
normalized telemetry model
        ↓
WebSocket
        ↓
React client
```

The frontend reports connection state, reconnects with a small increasing delay,
and keeps the last received snapshot visible during a temporary disconnect. No
persistence or real vehicle hardware is required for this milestone.

## Architectural constraints

Prefer:

- explicit component boundaries
- dependency inversion around hardware
- normalized application models
- replaceable data providers
- minimal runtime dependencies

Avoid:

- direct hardware access from UI
- giant service classes
- speculative abstractions
- infrastructure added before it is needed
- coupling domain/application logic to Raspberry Pi specific APIs
